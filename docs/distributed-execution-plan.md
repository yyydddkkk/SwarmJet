# 执行节点、网络配置与跨机器镜像分发计划

日期：2026-09-22。状态：已实施并完成双主机验收，见 [验收记录](distributed-validation.md)。本文件保留设计约定，部署方式以 [仓库与构建服务](registry.md) 为准。

## 1. 目标与已确认决定

本次完成可用的跨机器镜像分发、节点管理、网络配置和能力调度，不仅预留接口。用户在确认计划后已授权实施；验证不启动真实 Agent 或模型调用。

- 平台统一启用 Agent，新安装默认不启用任何 Agent；项目选择默认 Agent，Issue 用 `agent:codex` 等标签覆盖，不增加模型或代理标签。
- Worker 推进流程，Node 管理执行现场，Agent 在独立任务容器中执行。Agent 镜像可以安装多个 CLI，每次执行启动选定的 CLI。
- Node 与项目是多对多关系；一个宿主机可运行多个 Node，一个 Node 可运行多个项目的任务。
- 第一版一个 Node 对应一套执行环境，不新增独立的“执行环境”管理对象。
- 项目默认使用所有符合条件的节点，也可以限制允许的节点 ID 集合。
- 使用 Compose 管理独立、固定版本的 BuildKit 服务，缓存持久化；构建服务不绑定某个执行 Node。
- 使用自建 Distribution Registry，通过独立 Compose 部署并持久化存储；平台对接标准 Registry API，不提供页面自动安装仓库。单机可直接导入，多机通过仓库分发。
- 全局管理多份网络配置，构建服务和 Node 分别引用；支持“继承平台默认 / 直连 / 指定配置”。
- 任务固定 Node、镜像摘要及网络配置版本。配置修改默认仅影响新任务。
- 不自动迁移失联节点上的任务，不静默回退到本机、不替换用户指定的 Agent。

## 2. 当前基础及缺口

已实现的基础：

- `execution.Node` 封装工作区、Agent、联调、报告和清理；本机与远程实现共用流程。
- `swarmjet node` 自动注册并发送心跳，任务记录 `NodeID`，后续阶段固定路由。
- `Store.CreateTaskScheduled` 原子分配节点，目前只检查在线状态和容量。
- Agent 镜像随项目快照进入任务；任务与角色的 CLI 配置、会话已有隔离机制。
- 已有单机镜像配置、构建日志、取消和显式应用流程。

本次补齐：

- 节点管理、项目节点范围、节点镜像与 Agent 能力上报。
- 节点本地执行配置解析，替代仅由 Worker 环境决定 Agent 环境的行为。
- 将本机文件式镜像管理扩展为控制面持久化的构建和发布记录。
- 镜像发布、远程预拉取、摘要验证、就绪状态及失败重试。
- 代理配置版本、加密凭据、同步状态和实际执行位置的连通性检查。
- 每节点配置终端与 CLI 配置检查，确保“已安装 CLI”与“可以执行”有明确区别。

现有 `docs/execution-nodes.md` 描述的是当前行为；实施时再同步更新，避免把计划写成已交付能力。

## 3. 职责和部署关系

| 对象 | 职责 | 持久状态 |
| --- | --- | --- |
| 控制面 API / 调度 | 配置、授权、任务分配、节点状态、发布记录 | PostgreSQL |
| Worker | 推进 Temporal 流程，按任务快照调用节点 | 流程状态由 Temporal / 数据库管理 |
| 构建执行服务 | 调用 BuildKit、发布镜像、记录构建状态与日志 | 构建记录、日志；BuildKit 缓存卷 |
| 镜像仓库 | 保存可跨机器拉取的成品镜像 | 用户管理的仓库存储 |
| Node | 拉取镜像、准备代码、管理任务容器与验证环境 | 独立 DATA_DIR、节点本地镜像缓存 |
| Runner | 运行指定 Agent CLI | 私有任务目录和角色会话 |

构建执行服务可以复用平台二进制的独立运行模式，无需新增一套应用；不让每个普通 Worker 都启动一个镜像管理器。构建任务使用持久状态和租约，防止多副本重复执行；第一版并行构建数保持为一。

单机可同机部署全部服务。分布式把 Node 部署到其他机器；同机多个 Node 必须使用独立 ID、数据目录、服务地址和 Compose 项目名。共享 Docker daemon 时也共享镜像存储和 daemon 级代理，不声称它们是独立 Docker。

BuildKit 容器不能解决宿主机内核过旧的问题。安装预检检查内核、Docker、架构、存储与挂载能力；构建机器和运行机器分别检查，不以“容器化”替代兼容性验收。

## 4. 配置与数据模型

以下为职责级模型，具体表名和接口名称在实施时依现有约定确定。

### 4.1 网络配置

- 保存名称、HTTP/HTTPS 代理、NO_PROXY、可选软件源配置和版本。
- 代理认证信息加密存储，复用现有 secretbox；普通读取只返回是否配置、脱敏值和凭据引用。
- 平台默认配置是可变引用。任务或构建创建时解析为不可变版本，不能在执行中重新读取最新默认值。
- 支持证书配置引用，覆盖企业代理或私有仓库 CA；默认验证 TLS，不通过关闭证书校验解决连接失败。
- 历史配置版本在仍被任务引用时保留。普通更新不影响旧任务；凭据撤销优先于可重现性，撤销后旧任务明确阻断，不静默使用新凭据。
- 不将凭据写入项目/任务 JSON、Temporal 历史、命令行、镜像层、构建证明材料或可下载日志。

### 4.2 Node

- 管理配置：名称、是否接收新任务、容量、网络配置选择、默认 Agent 镜像发布版本。
- 上报状态：心跳、架构、协议版本、配置应用版本、镜像就绪状态、检测到的 CLI、配置检查结果及失败原因。
- 区分 desired 配置和 applied 配置，页面显示待同步、已生效、失败。
- 心跳只能更新节点观测状态，不能覆盖管理员的停用和配置决定。
- 注册不能直接取得任意项目凭据。节点调用沿用现有认证协议，并检查身份与节点配置访问范围；本次仍以受信任的管理员管理节点为使用范围，逐节点凭据与撤销机制应在节点管理中明确实现，避免全局共享密钥充当节点间权限隔离。
- Node 配置默认镜像用于新任务解析。项目已有显式角色镜像继续作为覆盖配置；优先级为项目显式镜像 > 节点默认镜像。新项目不把平台默认值复制成永久显式覆盖。

### 4.3 项目与任务

- 项目增加节点选择策略：自动或指定节点集合；空的指定集合是无效配置，不能解释为全部节点。
- 任务保存解析后的 NodeID、各角色镜像仓库摘要、网络配置版本、节点配置版本和 Agent；只保存凭据引用。
- 任务创建快照与容量分配在同一一致性边界完成，避免检查后配置变化导致错误接单。
- Node 默认镜像不要求只包含一个 CLI；平台启用状态与节点镜像中的 CLI 能力分别校验。
- 托管项目初始化也应使用明确选定的节点和环境，记录初始化归属；保留现有受限 OpenCode 初始化策略，不在本次扩展初始化 Agent。若缺少初始化能力，明确提示，不因任务可运行而误报初始化可用。

## 5. 镜像构建与跨机器分发

1. 用户选择 CLI、构建参数、目标架构、构建网络配置和目标仓库路径，保存构建快照。
2. 构建执行服务通过受控连接调用 Compose 管理的 BuildKit；构建上下文继续只包含必要模板文件。
3. BuildKit 使用独立缓存卷及资源限制；配置缓存回收上限，不删除正在使用的状态。
4. 构建成功后推送到配置的仓库，验证 manifest，保存 `registry/repository@sha256:...` 和架构元数据。
5. 发布成功与应用分开。用户选择目标节点应用，控制面保存 desired 发布版本，Node 预拉取并检查。
6. Node 使用只读仓库凭据拉取指定摘要，检测所需 CLI 的存在和版本，不调用模型；验证通过后标记 ready。
7. 新任务只使用该节点已经就绪且与任务要求匹配的镜像。正在分发的版本不替换当前已生效版本。
8. 回滚重新选择历史发布版本，对目标节点重复准备流程；已有任务继续使用原摘要。

需要区分三种标识：构建标签、仓库 manifest digest、本地 Docker image ID。跨机分发不能使用本地 image ID 代替可拉取的仓库摘要。

第一版构建原生目标架构镜像并记录平台信息；混合架构节点必须有对应构建产物，不自动启用 QEMU 或假设 amd64 镜像可运行于 arm64。多架构 manifest 自动组装不作为本次必需项。

构建状态至少区分构建中、发布中、成功、失败、取消、重启中断。推送失败不得标记发布成功。节点分发状态单独记录排队、拉取、验证、就绪、失败，支持幂等重试；局部失败不撤销其他节点已成功的发布，也不能把失败节点标记为可调度。

构建身份使用仓库推送权限，Node 只需拉取权限。认证文件和证书使用私有临时目录或受控凭据存储，完成后清理；真实构建凭据不进入镜像。

单机保留直接导入途径，但标明“仅本机可用”。历史本地镜像未发布到仓库前不得宣称支持远程分发。仓库预检验证地址、认证、权限及目标路径；第一版提供一个独立的 Distribution Compose 部署示例，包含持久化、TLS 和认证配置入口，不提供页面安装和全仓库清理。推送/只读拉取权限需要支持 scope 的认证授权服务或经验证的代理规则，不能声称 Distribution 的基础密码认证本身就能区分读写权限。

## 6. 代理应用与隔离

| 网络操作 | 配置应用位置 | 检测位置 |
| --- | --- | --- |
| 首次安装平台 / BuildKit 镜像 | 部署所在 Docker daemon | 安装预检 |
| BuildKit 拉基础镜像、推成品镜像 | BuildKit 服务代理、registry 配置 | 构建环境 |
| 构建步骤下载依赖 | 临时构建代理参数、软件源 | 实际构建步骤 |
| Node 拉成品镜像 | Node 所用 Docker daemon | 目标 daemon 的实际拉取 |
| 准备仓库、主机侧验证操作 | Node 启动子进程时的受控环境 | Node |
| Agent CLI / 容器内依赖下载 | 创建任务容器时注入 | 任务等价网络中的检查容器 |

平台代理配置不自动修改宿主机 daemon，也不自动重启 Docker。安装工具提供 daemon 配置指引与检测；节点页面独立显示镜像拉取网络是否就绪，不能把 Agent 代理测试通过视为镜像拉取通过。

Node 的网络选择覆盖 Worker 传来的通用代理变量，避免 Worker 接手变化导致出口变化。模型与 Git 凭据保持原有按角色授权，不能把网络配置和模型凭据混在一起。Node 控制面通信使用部署侧明确的网络规则，变更任务代理不得切断节点心跳。

直连模式要清除上下层代理遗留，明确处理大小写代理变量与 ALL_PROXY，不能只是不设置新变量。NO_PROXY 默认建议包含平台内部服务与内网地址，并允许管理员调整。不同工具对代理与 NO_PROXY 的支持需要用实际 CLI/HTTP 栈验证，不保证环境变量可以强制接管所有流量。

每节点配置终端使用该节点的网络配置、共享 CLI 配置目录和选定镜像；任务继续获取私有配置快照，不共享可写会话。节点配置更新时不得强行销毁已有终端。

隔离第一版面向受信任节点：独立数据目录、任务挂载、受控环境变量、任务/节点网络与资源限制；Agent 不挂 Docker socket。共享宿主机 Docker 的 Node 管理进程不是强安全隔离。代理选择不等于出口强制限制；禁止直连、防火墙策略、独立虚拟机等不在本次默认范围内。

## 7. 调度与故障语义

候选条件按顺序为：项目允许的节点 → 在线且接单 → 平台启用 Agent → 节点架构/镜像/CLI/配置就绪 → 有剩余容量。符合条件后按负载分配，事务内固定任务快照。

- 容量不足：等待并展示原因。自动扫描保留未认领状态、下一轮重试；手动请求明确返回可重试结果，不创建无执行归属的半成品任务。
- 能力不满足：展示缺少镜像、CLI、配置或节点范围不匹配等具体原因，不静默降级。
- 节点失联：沿用当前 blocked 与重试机制，保留工作区和归属，恢复后接管原执行；不新增自动迁移。
- 停用节点：不接新任务，已有任务仍可继续、取消、查询和清理。
- 删除节点：有非终态任务时禁止；还需检查历史报告与待清理资源引用，优先归档而非物理删除。归档身份不能被旧进程心跳重新启用。
- 同机多个 Node：每节点容量分别统计，同时明确宿主机总资源仍共享；设置任务资源限制，避免把多个容量值误当成新增物理资源。
- 检查当前全局 `agent-slot` 租约逻辑：分布式执行槽应按 Node 隔离，Worker Activity 并发与 Node 执行容量分开控制，防止扩容后仍被单机全局槽限制。

## 8. 页面与接口范围

- **网络配置**：配置列表、平台默认、编辑版本、脱敏凭据、实际使用位置的测试结果。
- **镜像配置**：构建参数、构建网络配置、仓库、日志、发布摘要、目标节点分发状态、应用与回滚。
- **执行节点**：状态/容量/任务、网络配置、默认镜像、Agent 检测、配置同步状态、配置终端、暂停接单、归档。
- **项目管理**：默认 Agent、自动或指定节点范围，解释不满足条件的原因，不复制全套节点配置。
- **添加节点**：生成部署说明和注册凭据，节点 Compose 启动后注册；不做 SSH 远程安装。

管理写接口继续使用会话认证、CSRF 防护和输入校验；节点协议扩展配置同步、镜像准备、能力检查和节点 runtime-admin 路由。长时操作返回操作 ID 并查询状态，不保持一个无限 HTTP 请求。凭据和密钥操作进入不含明文的审计记录。

## 9. 兼容与迁移

- 历史任务保留空 NodeID、本地镜像 ID、原 CLI 配置快照等语义，不重写为新节点或新镜像。
- 老项目默认采用自动节点选择；已有显式镜像配置保持有效，缺少跨机可拉取信息时给出迁移提示。
- 原本机 active 镜像导入为本地发布记录，不能直接成为跨机发布版本。
- 网络配置初始不强行启用代理；现有部署环境代理迁移需显式识别和提示，避免升级意外切断网络。
- 新统一调度路径可将本机执行能力表示为明确的本地节点；历史空 NodeID 路由继续兼容。新的分布式任务不得使用隐式本机 fallback。
- API、Worker、Node 协议版本与能力握手；旧 Node 缺少新配置/镜像准备能力时显示待升级，不下发它无法解释的任务。
- 若修改 Workflow 决策顺序，按仓库约定使用 Temporal 版本化并验证旧历史 replay。

## 10. 实施顺序与验收

### 阶段一：配置和节点模型

实现数据库迁移、版本化网络配置、仓库凭据、节点 desired/applied 状态、项目节点范围、任务执行快照和节点认证生命周期。

验收：旧数据迁移成功；默认无 Agent/代理被自动开启；敏感值不出现在响应和任务历史；心跳不覆盖管理配置；错误或撤销身份不可读取其他节点配置。

### 阶段二：BuildKit 和镜像发布

实现 Compose 构建服务、缓存和资源限制、构建租约、仓库发布与不可变摘要记录，兼容本机导入。

验收：日志、取消、重启中断、推送失败、重试与显式应用正确；多 Worker 不重复构建；旧镜像不会因失败被替换；构建代理不进入成品镜像。

### 阶段三：节点分发和执行环境

实现摘要预拉取、架构和 CLI 检查、配置同步、Node 与 Agent 网络注入、每节点配置终端。

验收：发布到至少两个独立 Docker daemon；目标环境不同本地缓存，仍可拉取并验证同一仓库摘要。断网、认证失败、错误架构均有明确状态；单节点失败不伪装全局成功。无需调用模型完成这些检查。

### 阶段四：能力调度和页面

实现所有页面、候选解释、Node 容量隔离、停用与归档、项目限制、初始化环境选择。

验收：一个项目可调度多个节点，一个节点可执行多个项目；不同网络环境和镜像任务正确分流；节点停用后老任务继续、新任务改派；配置更新不改变已创建任务；初始化保持受限工具策略。

### 阶段五：跨机器闭环及部署文档

用无模型调用的确定性测试执行器验证：构建 → 仓库发布 → 两个执行节点准备 → 任务分配 → 执行 → 结果与清理。两个独立 daemon 的集成测试不能替代真正的跨主机网络验收；交付时安排两台主机或独立虚拟机验证，并记录环境和结果。

分别验证构建网络与运行网络的直连/代理组合、NO_PROXY、配置变更、断线恢复、镜像回滚和凭据脱敏。运行受影响 Go 测试、必要集成测试、前端构建及页面测试；不运行真实 Agent 或模型，不用全量昂贵测试替代针对性验证。

更新安装文档、API 契约、执行节点文档，给出单机、多 Node 同机、多机、私有仓库和大陆网络部署示例。安装阶段的 Docker 拉取代理与页面中的执行代理明确分开。

## 11. 非目标及实施前环境信息

## 实施补充

新版单机部署也注册一个暂停的 local Node，作为镜像分发目标；管理员完成配置后启用。历史空 NodeID 任务仍在原本机路径继续，存在受管节点时新任务不静默回退。Node 支持默认镜像及最多 20 个额外预加载镜像，角色镜像按各自就绪能力检查。

私有 CA 和镜像仓库 mirror 当前属于部署配置（BuildKit 配置和 Docker 信任目录），不通过页面自动修改宿主机。页面管理代理和构建软件源；HTTP/HTTPS 代理使用普通 HTTP 代理协议及 CONNECT，不提供透明代理或原生 SOCKS 入口。
