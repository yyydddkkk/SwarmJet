# 第八轮：星图前端优化与 PR 读取提速

日期：2026-10-20。第七轮把星图做成了真实前端，但用真实数据一跑问题很多，见 [frontend-issues-round7.md](frontend-issues-round7.md)（下称"问题清单"，共 27 条）：
- 长文本不折叠；
- 历史对象全部上图；
- 几乎没有动画；
- 二级页面和设计稿差别很大；
- 首屏要等二十多秒。

这一轮把这些问题全部解决，同时把设计稿新增的"历史繁星"和"星系内部聚合"做进产品。

## 已定决策

- **设计稿是唯一的视觉标准，必须严格还原。** 依据是 [design/stars/index.html](../../design/stars/index.html)（本轮已更新）和 [frontend-stars-design.md](frontend-stars-design.md)（本轮新增第 10 节）。
  - 设计稿里已有的界面，直接移植它的 DOM 结构和 CSS 规则：字号、字体、间距、细线边框、斜体、过渡、交互方式都要一致。类名可以改，样式不能重新发明。
  - 设计稿用文字切换的地方（例如"显示"菜单里的"经典 / 简洁""明亮 / 纸本 / 夜空 / 跟随系统"），不得换成原生下拉框或复选框。
  - 设计稿没覆盖的界面（例如模型凭证表单、方法论文件编辑），用设计稿已有的元素推导：附录式面板、细线表格、斜体按钮、同一套颜色变量。PR 里逐个列出这些界面和推导方式。
  - 觉得设计稿某处不合理，先在汇报里提出，由用户决定，不要自行改。
- **第七轮规格里"空闲时不持续重绘"作废。** 改为：
  - 允许环境动画，也就是设计稿里的全部运动；
  - 页面隐藏时停止；
  - 系统开启"减少动态效果"时只保留静态画面；
  - 用帧耗时数据证明开销可接受。
- **命名**：继续用大白话（设计文档第 2 节）。后端返回的已知英文原因要转成中文短语；未知原因显示"其他原因"，原文放进可展开的详情。
- **本轮允许一处后端改动**：只改 PR 列表的读取性能（任务 A）。其他后端缺口照旧写进汇报，由用户决定。
- **"知道了"先存在浏览器本地**（localStorage，读写都包 try/catch），不加后端字段。
- **测试数据必须接近真实。** 第七轮的 mock 数据又短又干净，所以这些问题一个都没暴露。本轮的 mock 和 Playwright 测试至少要包含：
  - 3000 字的任务提示词；
  - 40 个以上已结束的 Agent（完成、取消、失败都有）；
  - 14 个以上开着的 PR，以及若干已合并的 PR；
  - 11 个以上 Issue；
  - 后端英文原因；
  - 900 条历史记录。
- **合并顺序**：B → A → D → E → C。B 是前端其他任务的基础，最先合；C 改动最大，最后合。

## 前端规则（任务 B 实现数据部分，C、D、E 只读结果）

### 文本

- **一行摘要**：用于列表、简报、标签、详情标题。
  - 来源优先级：关联的 Issue 或 PR 标题 → 任务的首句 → 角色名。
  - 超长截断加省略号。宽度按"汉字算 1、其他字符算 0.55"计算。
  - 星图标签上限约 14，列表约 40，简报约 30。
- **长文**：任务全文、验证结论、消息正文，在详情里默认收起成 4 行，点"展开"看全文。同一段内容不重复显示（例如任务全文和第一条消息相同时只显示一次）。
- **ID 和 sha**：默认显示短形式（sha 7 位，Agent 编号取末 8 位），点击复制全值。不在窄列里断行。
- **时间**：
  - 一天内显示相对时间："3 分钟前""5 小时前"；
  - 更早显示本地日期时间；
  - 不显示 ISO 原文。
- **英文原因转中文**：维护一张对照表，至少覆盖问题清单里见到的 `no attestation for the current head`、`verifier cancelled by control…`、CI 未通过、有新提交等。

### 什么上星图

| 对象 | 上图 | 不上图 |
|---|---|---|
| Agent | 工作中、空闲、停放、排队中 | 已完成、已取消（变成历史繁星或不画，见下节） |
| 失败的 Agent | 以 × 留在轨道上，直到用户点"知道了"或超过 24 小时 | 之后变成一颗偏暗的历史星 |
| PR | 开着的 | 已合并、已关闭 |
| Issue（signals） | 还没人接的，以及正在被活跃 Agent 处理的 | 已处理完的 |
| CI | 失败的 CI，挂在对应 PR 旁边 | 通过的 |

已合并的 PR 只在实时合并时播放"螺旋落入恒星加耀斑"，之后不再画。

### 历史繁星（设计文档第 10 节）

- **每颗星的来源**：
  - 每个已结束的 Agent 一颗；
  - verifier 不单独成星；
  - 取消的不画。
- **外观**：

  | 结果 | 外观 |
  |---|---|
  | 带来合并 PR 的 | 略大、略亮 |
  | 正常完成的 | 普通 |
  | 失败且已看过（或超时）的 | 偏暗 |

  - 6 小时内结束的，带一个很淡的十字闪光；
  - 亮度在 1 到 7 天内逐渐降到背景亮度。
- **位置**：由 Agent ID 哈希决定，刷新后不变。
  - 分布在 Issue 外圈之外，向外按指数变稀；
  - 扁度和星系一致；
  - 参数照搬设计稿的 `histPos`。
- **上限**：每个项目最多画 500 颗，更早的画成很淡的星尘。
- **结束时间**：以 `updatedAt` 近似。在设计文档和界面说明里注明口径。
- **交互**：
  - 项目层悬停显示"摘要 · 结果 · 多久以前"；
  - 点击弹出小卡片，显示完整摘要和"在列表中查看"；
  - 全部项目层不响应鼠标。
- **背景装饰星**：项目星空范围内去掉随机装饰星，避免和真实历史混淆。

### 星系内部

- **聚合**：
  - PR 轨道最多 9 个位置，按"等你决定 > 验证中 > 进行中 > 7 天没动静"排序，放不下的合成一个小簇，标注"还有 N 个 PR"；
  - Issue 外圈最多 6 个，没人接的优先，其余合成"还有 N 个 Issue"；
  - 点小簇弹出前 6 个和"在列表中查看全部"。
- **7 天没动静的 PR**：缩小、变淡。
- **标签**：按优先级逐个摆放，压到已有标签或主 Agent 的就不画。优先级从高到低：
  1. 等你决定
  2. 失败
  3. 小簇
  4. 工作中
  5. 验证中
  6. 没人接的 Issue
  7. PR
  8. 空闲
  9. 已被接走的 Issue

  另外：
  - 全部项目层只显示项目名和"N 件事等你"；
  - 悬停显示完整摘要。

### 动画（照搬设计稿）

- **环境运动**：工作中的 Agent 沿轨道运行，PR 缓慢漂移，verifier 绕 PR 转，主 Agent 的光芒缓慢旋转。
- **出生**：新 Agent 从恒星向外飞到自己的轨道；新 PR 由小变大。
- **完成**：彗星离开轨道向外飞，逐渐减速、变小，停在自己的历史星位置，落定时闪一圈。
- **合并**：PR 螺旋落入恒星，之后一圈耀斑。
- **⊙**：有事等你时外圈呼吸（设计稿的 `#observer.wait::after`）。
- **镜头**：
  - 点击或滚轮推近项目和对象，双击或 Esc 退回；
  - 镜头移动用设计稿的缓动。
- **面板**：简报、列表、图例、显示、对象详情、项目面板、平台设置、小卡片、⊙ 面板，进出都有过渡，时长和方式照搬设计稿 CSS。
- **帧率**：环境动画可以降帧（例如 30 fps）。

### 任务 A：PR 列表读取提速（后端）

````text
# 任务：让 GET /api/hives/{id}/prs 在有大量历史 PR 时也能秒开

## 背景
真实部署里，测试项目 `GET /api/hives/{id}/prs?state=all` 实测约 21 秒，是控制台首屏慢的主因。原因在 internal/api/prs.go 的 pullRequestList：
- 候选列表来自 ProjectPRs，包含这个项目所有历史 PR。已合并、已关闭的也每次都重新查一遍 GitHub。
- 每个 PR 依次串行调用 Merge.Check，每次都要请求 GitHub。
- cachedPR 在整个 GitHub 请求期间持有全局锁 prCacheMu，所有项目、所有请求都被串行化。
- 缓存只有 30 秒，过期后下一次打开又要付出全部代价。

## 要做的事
1. 合并或关闭是终态：
   - 第一次观察到后持久化 PR 的标题、状态、merged、closedAt、URL、head；需要的话新增迁移，编号接在现有之后。
   - 以后读取不再请求 GitHub。
   - webhook 收到 pull_request 事件时同步更新这份记录。
2. 开着的 PR：
   - 优先用一次 GitHub 列表请求（pulls?state=open，分页）拿到标题、head、状态；
   - 只对需要判断可否合并的 PR 做 readiness 检查；
   - 这些检查有并发上限（例如 4），同一个 PR 的并发请求合并成一次。
3. 网络请求期间不得持有全局锁。
4. 缓存过期后：
   - 先返回旧结果并在后台刷新；
   - 刷新结果有变化时，通过现有 swarmjet_events 机制发 pr 事件，前端按增量规则更新。
   - 合并操作仍以实时检查的 headSha 为准，不能因为缓存放宽 409 规则。
5. 单个 PR 查询失败时，不让整个列表 502。这一项标注"状态暂时无法获取"，其余照常返回。

## 约束
- 只改 PR 读取相关代码（internal/api/prs.go、internal/merge 的只读部分、internal/github 的列表请求、必要的 store 和迁移），不改合并、验证、派工逻辑。
- 不改 API 字段的含义。可以新增字段，例如单项的 `unavailable` 和整体的 `stale`，并写进 PR 描述。
- 不打印 token。

## 验收标准
- 新增测试覆盖：
  - 终态 PR 不再请求 GitHub；
  - 开着的 PR 走一次列表请求；
  - 网络请求期间锁已释放（两个项目并发读取不互相阻塞）；
  - 过期后返回旧结果并发出 pr 事件；
  - 单项失败不影响整体。
- 用假的 GitHub 服务模拟每次请求 1 秒延迟、15 个历史 PR、3 个开着的 PR，给出测量数据：
  - 冷启动首次读取不超过 3 秒；
  - 缓存命中不超过 300 ms；
  - 每次读取的 GitHub 请求数。
- 带 TEST_DATABASE_URL 的 `go test -race -p 1 ./...` 通过。

## 交付
分支 perf/pr-list，向 dev 开 PR。描述里写原因、改法、测量数据、新增字段和迁移。
````

## 集成与验收

1. **开发顺序**：B 和 A 并行开始。B 的 PR 审查通过后，C、D、E 从 B 的分支并行开发。
2. **审查**：重点看"是否忠实于设计稿"。逐个对比 PR 里的并排截图，并自己打开设计稿和实现对照：
   - 原生控件代替文字切换、面板没有过渡、字体字号不一致、文字透出，一律退回修改；
   - 界面里不得出现隐喻词（星系、恒星、彗星、在轨、熄灭、附录、星表）或 Hive、Queen、Forager 字样。图例说明可以用"做完的事""放不下的 PR"这类大白话。
3. **集成**：按 B → A → D → E → C 合并到集成分支，每次合并后跑 `cd web && npm run build`。
4. **全量测试**：
   - 带 TEST_DATABASE_URL 的 `go test -race -p 1 ./...`；
   - `python3 -m unittest discover -s deploy -p 'test_*.py'`；
   - compose config 校验；
   - `cd web && npm ci && npm run build && npx playwright test`。
5. **开集成 PR**，等用户批准后合并。
6. **升级部署后做真实验收**：本机部署 sj-r3，测试项目已有 40 多个历史 Agent 和 14 个 PR，正好是真实规模的数据。用真实浏览器验证：
   1. 首屏耗时：记录打开到简报完整显示的时间，以及 PR 接口的冷、热耗时，和第七轮的 21 秒对比。
   2. 星图：
      - 项目层只有当前对象；
      - 历史 Agent 成为外层繁星，悬停能看到摘要；
      - 没有文字重叠；
      - 环境动画在运行；
      - 点击能进入项目层。
   3. 简报、列表、对象详情：没有整段任务文字，长文能展开；时间、原因都是中文。
   4. 和设计稿并排截图：简报、列表、图例、显示、对象详情、项目面板、平台设置，在明亮、夜空主题下各一张。
   5. 在测试仓库创建一个小 Issue（先告诉用户内容），看到派工、PR、验证。征得用户同意后从 ⊙ 合并，看到合并动画，以及 worker 飞出变成历史星。
   6. 断开再恢复 api 服务，界面提示断线，恢复后正确刷新，且不重复拉快照。
   7. 结果写进 docs/claude/acceptance-round8.md，截图放在 docs/claude/acceptance-round8/，截图里不能出现任何凭证。
