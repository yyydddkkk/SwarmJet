> 初始化仅静态读取仓库并创建 Meta 仓库、生成项目说明，不安装依赖、不启动业务服务、不执行构建或测试。历史验证失败的项目可点击重试，保留已有分析结果并完成初始化。开发任务的验收配置独立于 Meta 仓库初始化。

# 快速接入

本文描述普通用户的最小接入路径。你只需要 GitLab 地址、一个有 `read_api`（或 `api`）权限的 Access Token，以及一个可用的模型服务登录。

## 1. 连接 GitLab

打开控制台的“新建项目”，填写 GitLab 地址和 Access Token，点击“验证并继续”。

- 服务端会向该地址请求 `/api/v4/user` 验证 Token，不跟随重定向，因此 Token 不会泄露到其他地址。
- 验证成功后连接被加密保存，后续项目可以直接复用；也可以点击“更换”重新验证。
- 需要独立合并身份时，在“高级”里填写合并 Token。它会单独验证；留空则开发与合并共用同一个 Token，此时没有独立 Token 的权限隔离。

## 2. 选择子仓库

系统分页读取该 Token 可访问的仓库，支持搜索。勾选需要一起开发的仓库，并确认每个仓库的目标分支（默认取仓库的默认分支）。

同一个项目的目标分支决定 MR 合并到哪里；不同仓库可以不同。目标分支不存在时初始化会提出具体问题，要求你确认分支或创建起点，而不是静默回退到 `main`。

## 3. 确认项目与合并策略

确认项目名称和受管 Meta 分支（通常 `main`），并设置“自动合并”：

- 新项目默认关闭。
- 关闭时，系统仍会开发、验证、创建 MR 并审查，但不会发起合并；只有检测到你在 GitLab 人工合并了全部 MR 后才收尾并关闭来源 Issue。
- 开启时沿用现有门禁：有效审查、当前提交验证、CI、目标分支检查，以及敏感变更的人工作业批准。
- 关闭开关与“等待敏感变更批准”是两件事：批准不能越过关闭的开关。

## 4. 配置 OpenCode

在页面内嵌终端中自行执行：

```sh
opencode auth login
```

终端通过已认证的 WebSocket 连接到 Worker 的隔离配置环境。系统不会自动操作用户账号，也不读取或展示登录秘密；终端内容不会被录制或持久化。关闭终端后登录配置保留，可再次打开修改。

点击“检查并继续”读取模型目录，选择模型后必须点击“验证模型”做一次最小实际调用。检测到配置文件或模型名称不等于凭据有效。

## 5. 自动初始化

点击“创建项目并开始初始化”。系统会：

1. 创建并托管内部 Meta-Repo（默认不在 GitLab 新建远程项目，不需要建仓库权限）。
2. 在固定提交的只读分析副本上运行初始化 Agent，生成项目说明、仓库关系、开发指南和构建/测试说明。
3. 在独立的可写副本中以隔离容器执行验证命令（需要部署配置 `INIT_VERIFY_IMAGE`；未配置时验证会被阻断）。验证容器使用确定性名称并在取消、超时或 Worker 重启后强制删除，不依赖 docker 客户端存活。

页面展示进度、生成的文件和验证结果。缺少信息时会在页面提出具体问题，保存回答后继续；失败可以重试；运行中可以取消。初始化是持久化任务，Worker 重启后会继续。

状态分为三步：仓库已连接、分析完成、可以接收开发任务。只有“可以接收开发任务”时才建议启用项目。无法识别测试命令时会明确标记“尚未完成验证”，不会自动接单。

## 6. 启用与后续

初始化完成后可查看或编辑生成的说明（位于受管 Meta-Repo），必要时在项目编辑器补充验收检查，再手动“启用项目”。

## 高级入口：导入已有 Meta-Repo

已有 Meta-Repo 的团队仍可在项目编辑器中填写 Meta-Repo 地址并读取清单，行为与之前一致；仓库清单必须与 `.meta.yaml`、`.meta.yml` 或 `.meta` 一致。

## 部署要点

- `SWARMJET_MASTER_KEY`：加密保存连接 Token 的主密钥。生成一次（`openssl rand -hex 32`）并长期保持不变、单独备份。丢失后旧 Token 无法解密，需要重新录入。
- `INIT_VERIFY_IMAGE`：用于在无网络隔离容器中执行初始化验证命令的镜像；未设置时验证被阻断，不会以 Worker 进程身份运行模型生成的命令。
- 受管 Meta-Repo 与分析副本位于控制面 `DATA_DIR`，需纳入备份，且不会被单任务保留期清理删除。受管 Meta-Repo 在任务准备阶段以 git bundle 传输到被分配的执行节点，因此受管项目可调度到任意在线节点；分布式模式下控制面 Worker 仍需 Docker 与 `INIT_VERIFY_IMAGE` 完成初始化。

## 当前限制

- 初始化协调器使用 PostgreSQL 状态 + 按项目租约，不是 Temporal Workflow；任务的开发/验证/合并仍完全由 Temporal 控制。
- 初始化验证强制在 `INIT_VERIFY_IMAGE` 容器中执行；未配置时验证被阻断而不是降级到 Worker。工具链需由该镜像提供。
- 只有一个 GitLab 连接 Token 时，合并与开发共用同一凭证。
- 尚未实现从控制台直接编辑受管 Meta-Repo 中的文件；需要编辑时走 Git 工作流或后续版本。

## 可选：发布 Meta 仓库到 GitLab

初始化完成页提供“发布到 GitLab”。可选择群组或个人空间创建私有仓库，也可关联已有的空仓库；已有文件的仓库会被拒绝。页面会显示目标路径，点击“确认发布到 GitLab”后由 Worker 执行。Token 需要 API 与仓库写入权限，新建仓库还需要空间的创建权限。

发布意图、目标和固定 Meta 提交保存在初始化记录中。网络或权限错误不影响本地初始化成果；重试继续使用同一目标，不重复创建仓库、不覆盖远程分支。推送跳过 CI，不执行仓库代码。

发布成功后显示远程链接。GitLab 是共享内容来源：新任务准备时拉取远程 Meta 分支，再按已有任务工作区机制固定版本。团队通过 GitLab 分支和 MR 更新说明；当前不提供自动重新分析并创建文档更新 MR 的入口，平台不会自动推送覆盖人工修改。
